# سعي دليل التنفيذ التقني باستخدام Supabase

قرار نطاق النموذج الأولي — 5 أكتوبر 2026: تستهدف سعي كلية الهندسة وعلوم الحاسب فقط في الفرص وجهات التعلم وتجربة الطلاب الأولى. يختبر الطلاب النموذج قبل التوسع. إضافة الكليات الأخرى مؤجلة إلى مرحلة مستقبلية بجانب الأندية والملف الشخصي العام وملف الإنجازات. يبقى الحساب البسيط للمحفوظات والاهتمامات والتجارب ضمن النطاق؛ هذا تحديد للمحتوى والجمهور المستهدف، وليس تحققًا من الانتماء الجامعي أو منعًا للزائر من التصفح.

مرجع التفاصيل الأحدث — 5 أكتوبر 2026: [مرجع الإصدار الأول](../RELEASE-1.md). تعتمد حقوله وصلاحياته وعقده عند تعارض مثال تقني هنا معه. تمت مزامنة نسخ Word وPDF مع تحديث نطاق النموذج الأولي؛ يبقى RELEASE-1.md المرجع التفصيلي للعقد.

الإصدار 2.0 — 4 أكتوبر 2026

القرار المعتمد: Supabase وحده للحسابات وقاعدة البيانات والصلاحيات. تستخدم المنصة Supabase Auth وPostgreSQL وسياسات RLS. خدمة الذكاء الاصطناعي منفصلة وتستدعى من Edge Function. لم يتم تنفيذ الاتصال بالخدمات بعد؛ هذه تعليمات التنفيذ وليست إعلانًا عن جاهزية المنصة.

تعيد هذه النسخة صياغة تعليمات المزود السابق وأوامره وقواعده بما يناسب القرار الجديد. النسخ السابقة محفوظة في سجل Git. لا يعتمد الفريق أمثلة الإعداد القديمة أو جداول تنفيذ الصوت والجلب الآلي في النسخة الحالية.

## 1 نطاق النسخة الحالية

الزائر يتصفح الفرص وجهات التعلم وتجارب الطلاب دون حساب. الطالب المسجل يحفظ العناصر ويدير اسم العرض والاهتمامات ويرسل تجربة نصية للمراجعة. المسؤول يضيف المحتوى ويعدله ويخفيه ويعتمد التجارب. المنشور الأصلي للفرصة يبقى كما هو مع رابط المصدر، والذكاء الاصطناعي يصنف النوع والمجالات فقط.

التوسع إلى الكليات الأخرى، والأندية والمجتمع والمحادثات وتكوين الفرق والملف العام والإنجازات والمشروعات والشهادات ورفع الملفات والصوت وإعادة الصياغة والتوصية الشخصية والجلب الآلي الشامل مؤجلة. الروابط الرسمية للفرص والجهات تبقى متاحة؛ لا ينشأ سجل مرفقات للطالب.

## 2 بنية المشروع وطريقة الربط

الواجهة العاملة موجودة في interface-prototype/dist. تستخدم حاليًا JavaScript وHTML وCSS؛ لا يشترط تحويلها إلى React لإكمال الربط. يحتفظ الفريق بالتصميم والصفحات الحالية. يعمل التطوير في ux-amal، ولا يغير main دون طلب المالكة.

ينفذ مسؤول التأسيس محولًا يعرّف window.SAI_BACKEND قبل تحميل services.js. المرجع لأسماء الدوال هو INTEGRATION.md في مجلد الواجهة. يبقى services.js الحد الفاصل بين الشاشات والخدمات. تستخدم الدوال Supabase وتعيد Promise ونتيجة واضحة أو خطأ آمنًا. لا تدعي نجاح الحفظ إذا رفضت الخدمة الطلب.

توضع تغييرات مخطط قاعدة البيانات في ملفات SQL مرقمة تحت supabase/migrations عند بدء التنفيذ، ووظيفة تصنيف الفرص تحت supabase/functions. لا يعدل شخصان المخطط أو ملفات الحسابات المشتركة بالتزامن.

## 3 تأسيس المشروع مرة واحدة

1. ينشئ المسؤول مشروع Supabase باسم سعي ضمن حساب الفريق المعتمد، ويختار منطقة الاستضافة بعد مراجعتها.
2. يسجل إعدادات المشروع وملاك الوصول. لا تعد كلمة مرور قاعدة البيانات جزءًا من ملفات الواجهة.
3. يفعّل التسجيل بالبريد وكلمة المرور والتحقق من البريد، ويحدد Site URL وروابط العودة المسموحة للتجربة والنشر.
4. يجهز إرسال بريد التحقق والاستعادة ويختبره مع حسابات الفريق. يراجع متطلبات SMTP وحدود الإرسال قبل دعوة مستخدمين حقيقيين.
5. ينشئ الجداول والعلاقات وسياسات الوصول، ثم حساب طالبين ومسؤول للاختبار.
6. يربط دوال الخدمات بالواجهة، ويختبرها على جهاز العضو الآخر قبل توزيع الأقسام.

لا تفترض الخطة مجانية غير محدودة. تراجع حصص قاعدة البيانات والحسابات والوظائف وتكاليف مزود الذكاء الاصطناعي قبل الإطلاق، ولا تفعل خدمة مدفوعة دون اتفاق. استضافة ملفات الموقع قرار منفصل؛ Supabase ليس بديلًا تلقائيًا لاستضافة الواجهة الثابتة.

## 4 المفاتيح والإعدادات

الواجهة تحتاج رابط المشروع ومفتاح publishable. ظهور المفتاح العام متوقع، لكن صلاحيات قاعدة البيانات يجب أن تقيّد الوصول. مفاتيح secret أو service_role وكلمة مرور قاعدة البيانات ومفتاح مزود الذكاء الاصطناعي تبقى في بيئة الخادم فقط؛ لا توضع في Git أو ملفات الواجهة.

تستخدم المكتبة @supabase/supabase-js عند إعداد الربط. يحدد مسؤول التأسيس طريقة تحميلها المناسبة للواجهة الحالية. إن اعتمد الفريق Vite لاحقًا يمكن استخدام VITE_SUPABASE_URL وVITE_SUPABASE_PUBLISHABLE_KEY؛ هذه الأسماء ليست إعدادًا يعمل تلقائيًا في ملفات HTML الحالية.

تخزن وظيفة التصنيف مفتاح مزود النموذج ضمن أسرار Edge Functions. لا يرسل المتصفح مفتاح الإدارة ولا يعتمد النظام على role قادم من نموذج المستخدم لمنحه صلاحية مسؤول.

## 5 مخطط البيانات المستهدف

- auth.users: حسابات الدخول التي يديرها Supabase Auth؛ لا نخزن كلمات المرور في جداول التطبيق.
- profiles: id مرتبط بمعرف الحساب، وname وinterests وتاريخ الإنشاء والتحديث. لا حقول إنجازات أو شهادات أو مهارات في الحساب الحالي.
- admin_memberships: معرفات المسؤولين، ويضيفها مالك المشروع عبر مسار إداري موثوق. لا يملك الطالب تعديلها.
- fields وopportunity_types: قوائم التصنيفات المعتمدة ومعرفاتها الثابتة.
- opportunities: id وtitle وoriginal_text وsource_name وsource_url وregistration_url وtype_id وmode وdeadline_text وdeadline_at وstatus وclassification_status وpublished_at وupdated_at.
- opportunity_fields: علاقة متعددة بين الفرص والمجالات، بمفتاح مركب يمنع تكرار الوسم للفرصة نفسها.
- providers: id وname وdescription وdetails وurl وcontent_types وlanguage وcost وstatus وتواريخ المراجعة.
- provider_fields: علاقة الجهات بالمجالات المتعددة.
- saved_opportunities وsaved_providers: user_id ومعرف العنصر وcreated_at. يمنع مفتاح مركب تكرار الحفظ وتضمن العلاقات وجود العنصر.
- experiences: id وuser_id وtitle وbody وfield_id وstatus وcreated_at وpublished_at. تبدأ التجربة pending ولا ينشرها الطالب مباشرة.

هذه مواصفات تنفيذ وليست جداول منشأة. يحول المحول أسماء الأعمدة إلى الحقول التي تتوقعها الواجهة، مثل original_text إلى originalText. يجمع جدولي المحفوظات في نتيجة saved بالشكل {kind,id}. تستخدم المواعيد timestamptz، ويحفظ النص الأصلي للموعد أيضًا؛ الموعد غير المعروف null وليس تاريخًا مخمنًا.

## 6 الصلاحيات داخل قاعدة البيانات

تفعل RLS على كل جدول مكشوف عبر واجهة البيانات، مع مراجعة grants والسياسات لكل عملية. لا تكفي إخفاء الأزرار في المتصفح لحماية البيانات.

- الزائر يقرأ الفرص والجهات والتجارب المنشورة فقط والتصنيفات العامة.
- المستخدم يقرأ ويعدل بيانات حسابه فقط؛ ترتبط الملكية بـ auth.uid().
- المستخدم يضيف ويحذف محفوظاته فقط، ولا يقرأ محفوظات غيره.
- المستخدم يرسل تجربته بمعرفه وحالة pending فقط، ويقرأ حالة تجاربه الخاصة. لا تمنحه سياسة الكتابة حق اعتمادها.
- المسؤول المعتمد يدير المحتوى ويراجع التجارب. تتحقق الوظائف الخادمية من الحساب وصلاحية المسؤول أيضًا.
- جدول صلاحيات المسؤولين لا يقبل تعديلًا من الحسابات العادية. يراجع مسؤول التأسيس استعلام فحص الإدارة حتى لا ينتج استدعاء دائري لسياسات RLS.

تختبر الصلاحيات بطلبات فعلية من طالبين وزائر ومسؤول، لا بمجرد مشاهدة الصفحة. خدمات الإدارة التي تتجاوز RLS تستخدم في الخادم فقط وبأضيق نطاق لازم.

## 7 الحسابات والمحفوظات

يستخدم التسجيل Supabase Auth، ولا تبدأ الواجهة جلسة ناجحة لمجرد إرسال رسالة تحقق. تعالج العودة من رابط التحقق والاستعادة وتتيح تغيير كلمة المرور بعد التحقق من جلسة الاستعادة. يراجع المحول أخطاء الخدمة ويعيد رسالة مناسبة.

يسترجع النظام الجلسة عند فتح الموقع ويحدث الشاشات عند الدخول والخروج. لا تحفظ كلمة المرور في المتصفح أو السجلات. بعد الدخول يعود الطالب إلى عملية الحفظ التي بدأها. عند فشل الحفظ تبقى حالة الزر مطابقة للحالة المحفوظة فعليًا.

## 8 نشر الفرص وتصنيفها

يلصق المسؤول النص الأصلي والرابط ويختار مسودة أو نشرًا. يتحقق النظام من صلاحية المسؤول ومن صحة المدخلات ويحفظ النص دون إعادة صياغة. لا يحول انتهاء صلاحية الرابط وحده إلى ادعاء بانتهاء موعد الفرصة.

تستدعي Edge Function مزود ذكاء اصطناعي منفصلًا؛ اختيار المزود والنموذج لم يعتمد بعد. تتحقق الوظيفة من المستخدم وصلاحيته، وتطبق حدًا للطلبات وحجم النص والوقت، ثم تطلب نوعًا ومجالات من القوائم المعتمدة. يعامل المنشور كبيانات لا كتعليمات للنموذج.

يُفحص الناتج قبل حفظه: النوع من القائمة، والمجالات معرفات موجودة ويمكن تعددها. لا تعتمد مواعيد أو شروط مستنتجة. يحتفظ النظام بحالة pending أو completed أو needs_review أو failed للتصنيف، ويتيح تصحيح المسؤول وإعادة المحاولة. فشل الذكاء الاصطناعي لا يحذف المنشور؛ يظهر المنشور المعتمد ضمن كل الفرص دون وسوم عند الحاجة.

تُصنف الفرصة عند إضافتها أو تغيير نصها، لا مع كل زيارة طالب. لا يحتاج هذا المسار قاعدة متجهات أو تدريب نموذج. عند انتهاء deadline_at المعروف تستبعد الفرصة من القائمة الافتراضية؛ تعرض المحفوظات حالتها بوضوح. لا ينشر النظام مسودة لمجرد نجاح التصنيف.

## 9 جهات التعلم وتجارب الطلاب

تضاف الجهة باسم ونبذة ورابط رسمي ومجالات وأنواع محتوى. اللغة والتكلفة معلومات اختيارية لا تخمنها الواجهة. لا نجلب جميع دورات الجهة. يستطيع المسؤول تعديل الجهة وإخفاءها دون تعديل كود الموقع.

يشارك الطالب تجربة نصية ترسل للمراجعة. تعرض الإدارة قائمة المعلقات مع الاعتماد أو الرفض، ويرى الطالب الحالة. لا تنشر بيانات الحساب الخاصة مع النص. الصوت وإعادة الصياغة وتعديل التجربة المرسلة وحذفها ذاتيًا مؤجلة؛ تعالج طلبات الإزالة إداريًا في البداية.

## 10 تقسيم العمل بعد التأسيس

ينجز شخص واحد الأساس المشترك أولًا: الحسابات والجداول والسياسات والمحفوظات والمحول. معيار التسليم هو تشغيله على جهازي الفريق ونجاح اختبارات الوصول والحفظ.

بعده يمسك الشخص الأول الفرص بالكامل بما فيها الإدارة والتصنيف. يمسك الشخص الثاني جهات التعلم وتجارب الطلاب بالكامل. تتولى المالكة اعتماد المحتوى والمراجعة والدمج. أي تعديل في المخطط أو الحسابات يعود إلى مسؤول التأسيس. يعمل الجميع في فروع العمل المتفق عليها ويرفعون طلبات مراجعة دون دمج ذاتي إلى main.

## 11 الاختبار والنشر والتشغيل

قبل الإطلاق تختبر الحسابات والتحقق والاستعادة والجلسة، وعدم قدرة طالب على قراءة بيانات طالب آخر أو اعتماد تجربة، وثبات المحفوظات بعد إعادة الدخول. تختبر إضافة المحتوى وتعديله وإخفاءه، ومراجعة تجربة، وفشل التصنيف وإعادة المحاولة، وغياب النتائج وانقطاع الاتصال والجوال ولوحة المفاتيح.

تستبدل أمثلة العرض بمحتوى حقيقي موثق أو حالات فارغة واضحة. تستضاف الواجهة عبر مزود استضافة ثابتة يعتمد لاحقًا، وتضبط HTTPS وروابط عودة Auth. لا تستخدم أوامر استضافة المزود السابق. تفصل بيانات الاختبار عن الاستخدام الحقيقي ويحدد مسؤول النسخ الاحتياطي والاستعادة ومتابعة الأخطاء والحصص.

تبدأ التجربة بمجموعة صغيرة. لا يوجد وعد بإنجاز كامل خلال 20 يومًا قبل اجتياز التأسيس وتقدير قدرة الفريق. يسلم الفريق رابط النسخة، وسجل اختبارات القبول، وتعليمات التشغيل، وملاك الوصول، وحدود الخدمات والميزات المؤجلة.
